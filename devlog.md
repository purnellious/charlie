Three fixes: (1) Email topic self-heal — `core/tools/email/__init__.py`'s `poll_and_notify`/`send_alert` now go through a new `_send_to_email_topic` helper that catches a deleted-topic error directly on the send call and recreates it within one poll cycle (≤2 min); the old daily `reconcile_email_topic` job/function is removed entirely as redundant — this resolves BUG-017 for email by making the broken permission-gated probe unnecessary rather than fixing it (noted in bugs.md that `bugs.py`'s identical nightly reconciliation likely has the same permission wall and remains open, out of scope for this build). A new standalone `watchdog.py` (stdlib-only, no dependency on Charlie's own venv or modules — reads `.env` directly, deployed under a separate `com.charlie.watchdog.plist`, `StartInterval=300`) checks both process liveness (`launchctl list`) and heartbeat freshness (<10 min old); on newly-detected unhealthy it alerts via a raw Telegram API call and attempts exactly one automatic restart (`launchctl kickstart -k`), then falls back to alert-only (capped) if still unhealthy afterward, to avoid a restart-loop masking a deeper problem. This is a deliberate exception to the "never auto-restart without asking" norm elsewhere (`restart_charlie` still requires explicit confirmation for code-deploy restarts) — narrowly scoped to unattended health-failure recovery, signed off as a named Tier-3 risk. Deliberately a fresh implementation, not copied from Bartie's own `watchdog.py` (which only checks PID existence and would not have caught this incident at all, since Charlie's process never crashed — Bartie itself was separately fully stopped and disabled the day before, see above). BUG-010 (missing `/health` command) partially addressed by the new automated alerting half; the on-demand command itself still doesn't exist. `/security-review`: no findings meeting the reporting threshold (checked command-injection surface in `watchdog.py`'s two `subprocess.run` calls — both use fixed argument lists with no attacker-influenced input; the `.env` parser; the raw alert POST's interpolated text, traced to purely local health-check state; the auto-restart trigger path, gated strictly on local process/file state with no remote trigger; `_wait_for_network`'s hardcoded hostname; and the email self-heal's `BadRequest` handling for any topic-misrouting risk — none introduced a new exploitable path). Code review found and fixed 3 real issues: `_wait_for_network()` bounded each DNS attempt only between loop iterations, not on the blocking `socket.getaddrinfo()` call itself, so a resolver that hangs rather than errors (exactly the failure class this fix targets) could still block startup indefinitely — fixed by running each attempt in a fresh daemon thread with its own bounded `join(timeout=...)`, verified directly against a monkeypatched permanently-hung resolver; the email self-heal only matched a *deleted*-topic error, not a *closed* one, despite the docstring claiming both, which would also have silently broken the failure-alert's own delivery path — fixed by broadening the match and documenting why a closed Email topic gets replaced rather than reopened (unlike bug topics); `watchdog.py`'s `_restart_charlie()` never checked whether `launchctl kickstart` actually succeeded, so a failed restart (e.g. if `com.charlie` were fully unloaded rather than crashed) would silently consume the outage's one auto-restart attempt and tell Jonathan Charlie "was restarted" when it wasn't — fixed to check the return code and report failure honestly, verified against a simulated failed-kickstart result. Verified locally: all four changed/new files compile and import cleanly, `_wait_for_network` returns near-instantly on a healthy network and correctly bails out after its timeout against a simulated hung resolver, `watchdog.py`'s state-machine helpers (env parsing, process/heartbeat checks, state load/save, restart failure handling) tested directly in isolation without touching the real `com.charlie` service or sending a live Telegram alert.
